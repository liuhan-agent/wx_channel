# 微信视频号关键词入口 WebView 刷新设计

## 背景

关键词任务调用 `Invoke-WeChatKnownShareOpen.ps1 -EntryOnly` 后，入口脚本目前在确认微信主窗口尺寸后就输出 `wechat_channel_entry_sent` 并返回。脚本后半段已有定位视频号 WebView、发送 F5 刷新、再返回入口成功的逻辑，却被这个提前返回绕过。于是上层可能开始等待 ltaoo 页面桥接，而当前页面从未在临时代理就绪后刷新；`wechat_bridge_unavailable` 不能单凭这一点归因于分享链接。

## 目标与边界

- `EntryOnly` 的成功信号只能在唯一的目标 WebView 被定位且 F5 消息成功发送后出现；窗口找不到、候选不唯一或刷新消息失败时保留明确错误。
- 保留已经存在的微信启动、主窗口激活和登录确认等待；入口依旧不需要分享链接或地址栏。
- 不改证书安装/卸载、宿主机代理、分享链接导航或 ltaoo 桥接就绪判定。成功信号只表示“刷新已发送”，不表示桥接已连接；上层继续独立轮询桥接状态。

## 实现方案

删除主窗口尺寸检查后的 `EntryOnly` 提前成功返回，使执行到现有的 WebView 定位与 F5 发送路径。关键词模式在协议入口和登录确认之后直接等待 WebView，不进入专为链接导航准备的模板/地址栏回退；分享链接模式保留现有回退与地址栏校验。保留 `-Refresh` 的 `wechat_page_refresh_sent` 返回值，其余关键词入口仍返回 `wechat_channel_entry_sent`。只有成功发送 F5 才输出相应返回值；定位或发送失败时抛出现有错误。

这一小范围修复不增加额外刷新次数，也不把“桥接就绪”伪装成入口成功条件。若页面刷新后仍无桥接，由上层原有检测报告 `wechat_bridge_unavailable`，再依据日志继续诊断。

## 验证

- 调整现有脚本回归测试：要求 `EntryOnly` 的成功返回位于 WebView 定位及 F5 发送之后；测试仍要求保留登录确认逻辑、`-Refresh` 返回值和关键词入口对分享链接的独立性。
- 先观察改动前测试失败，再观察修复后通过；运行相关 Go 测试与 PowerShell 语法检查。
- 如进行真人联调，先按仓库要求记录分支、提交号、工作区、批准的 Go/CGO 工具链、实际构建产物、微信运行时、数据库和输出目录；临时宿主机证书与代理必须在联调结束后恢复和清理。真人联调结果与静态/单元测试结果分别报告，不以“F5 已发送”冒充“页面桥接已成功”。
